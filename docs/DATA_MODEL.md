# Data model and durability

## Storage ownership

The agent is the only SQLite accessor. Use a dedicated writer thread with bounded requests; queries also go through the storage module. Store data in per-user application directories, outside browser profiles and the repository. Development uses an isolated directory.

## Directories on Linux

Follow the XDG Base Directory specification; use the defaults when a variable is unset or not absolute, except `XDG_RUNTIME_DIR`, which has no safe default.

| Purpose | Location                                                     | Contents                                                                     | Mode                           |
| ------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------- | ------------------------------ |
| Data    | `$XDG_DATA_HOME/reopen/` (default `~/.local/share/reopen/`)  | `reopen.sqlite` with its WAL and shared-memory files, verified backups       | `0700` directory, `0600` files |
| State   | `$XDG_STATE_HOME/reopen/` (default `~/.local/state/reopen/`) | Rotated redacted logs, preserved corrupt-database evidence                   | `0700` directory, `0600` files |
| Runtime | `$XDG_RUNTIME_DIR/reopen/`                                   | Singleton lock and sockets ([Protocols](PROTOCOL.md#local-sockets-on-linux)) | `0700` directory, `0600` files |

Settings live in SQLite, not a separate configuration file. The XDG autostart entry (`$XDG_CONFIG_HOME/autostart/`) and native-host manifests are registration entries owned by the installer and setup flow, not agent data.

**Development isolation:** `pnpm dev:agent` and development builds use the directory name `reopen-dev` in place of `reopen` in all three locations, so development never opens production checkpoints, sockets or pairing records. Automated tests use fresh temporary directories passed explicitly to the agent and never resolve XDG locations. The repository's ignored `.dev-data/` directory may hold disposable local fixtures only.

Enable foreign keys, Write-Ahead Logging (WAL) and `synchronous=FULL`; set a bounded busy timeout. These settings support durable transactions but cannot guarantee survival of failing storage hardware. Use SQLite's backup API for live backups; copying only the main database while WAL is active is unsafe.

| `restore_actions`         | id, run_id, ordinal, resource_id, state, attempt_id, result_code                               |
| `settings`                | key, version, validated_value                                                                  |
| `schema_migrations`       | version, applied_at                                                                            |

All IDs are UUID strings generated by trusted components as appropriate. Timestamps are UTC ISO 8601; display in the user's local timezone. Use monotonic clocks for local deadlines, not wall-clock timestamps. Browser IDs and process IDs are transient observations, not durable resource identities.

Keep historical resource payloads immutable. JSON payloads are typed and versioned per resource kind; validate before storage and before restoration. Exclude secrets and raw process command lines. Use integer ordinals for stable order. Index checkpoint history by workspace/time, resources by checkpoint, browser captures by source/capture, and actions by run/ordinal.

## Source states

Use `complete`, `partial`, `unavailable`, `stale`, `excluded` and `unsupported`. A checkpoint is complete only when every enabled, required provider succeeded within policy. Disabled or explicitly excluded providers do not count as failures. Resource-level errors remain visible.

If fresh browser data is unavailable, a checkpoint may explicitly reference retained last-known browser state with its original capture timestamp and `stale` status. Do not relabel it as newly captured. Compare sequence only within a source epoch; reject delayed events from superseded connections.

## Atomic persistence

1. Collect provider results outside a write transaction under fixed deadlines.
2. Validate, normalize and compute a content hash from meaningful resource state, not timestamps.
3. Insert checkpoint, source statuses and resources in one transaction.
4. Commit before publishing success. If unchanged, update separate observation freshness without rewriting immutable history; “Save now” may create an explicit checkpoint.
5. Perform retention as a separate bounded transaction after success.

Browser chunks are temporary staging, never recovery checkpoints. Persist the fully validated browser capture and its ingestion ID in one transaction before acknowledging; duplicate ingestion IDs return the prior result. The next periodic or debounced capture combines fresh browser state and desktop providers.

## Recovery protection

At startup, in one transaction, identify the previous session's latest useful checkpoint, create a pending recovery candidate and add a candidate pin before new captures can run. Prefer complete checkpoints with supported resources; if only partial history exists, offer it with warnings. A verified all-empty capture remains valid history but is not automatically preferred over useful prior work. Concretely, the candidate is the previous session's newest checkpoint that has at least one resource, preferring `complete` over `partial`; a session with only empty captures adds no candidate, and earlier pending candidates stay protected. Closed candidate rows remain as history, so retention removes them explicitly before deleting their checkpoint.

Multiple unresolved candidates can exist across repeated restarts. Retention never deletes any referenced pending candidate or user-pinned checkpoint. Dismissing or successfully resolving a candidate releases only that candidate's pin. A failed, cancelled or uncertain restoration leaves protection in place. Starting a restore also pins its checkpoint until its journal is resolved.

## Retention and migration

Apply age and count limits only to eligible unpinned automatic checkpoints. Age is measured from the last observation (an unchanged state refreshes it), the count is ranked over all unpinned automatic checkpoints of a workspace, and a workspace's newest checkpoint is never deleted. Checkpoints referenced by a restore run are kept. Over the storage budget, the oldest eligible checkpoints go first; when nothing more is eligible the run reports that pins or manual checkpoints block compliance. Timestamps are stored as whole-second UTC text so text order is time order. Retain manual checkpoints until explicit deletion or a separately visible manual-retention policy. Enforce the storage budget without silently deleting pins; surface storage pressure when policy cannot fit. Bound staging and logs separately.

Migrations are numbered, transactional where SQLite permits, and tested against prior versions. Each migration and its `schema_migrations` row commit together. Tables are `STRICT` with `CHECK` constraints on state columns; `checkpoint_pins` and `recovery_candidates` reference checkpoints without cascading deletes, so the database itself refuses to delete a protected checkpoint. An existing zero-byte or unreadable database file is reported as corrupt and left untouched. Create a verified backup before destructive migration. An older agent encountering a newer schema must refuse writes with a useful error. Never silently create an empty replacement database after corruption; preserve evidence, disable writes and offer explicit backup recovery.
