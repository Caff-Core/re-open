# Data model and durability

## Storage ownership

The agent is the only SQLite accessor. Use a dedicated writer thread with bounded requests; queries also go through the storage module. Store data in the per-user local application data directory, outside browser profiles and the repository. Development uses an isolated directory.

Enable foreign keys, Write-Ahead Logging (WAL) and `synchronous=FULL`; set a bounded busy timeout. These settings support durable transactions but cannot guarantee survival of failing storage hardware. Use SQLite's backup API for live backups; copying only the main database while WAL is active is unsafe.

| `schema_migrations` | version, applied_at |

All IDs are UUID strings generated by trusted components as appropriate. Timestamps are UTC ISO 8601; display in the user's local timezone. Use monotonic clocks for local deadlines, not wall-clock timestamps. Browser IDs and process IDs are transient observations, not durable resource identities.

Keep historical resource payloads immutable. JSON payloads are typed and versioned per resource kind; validate before storage and before restoration. Exclude secrets and raw process command lines. Use integer ordinals for stable order. Index checkpoint history by workspace/time, resources by checkpoint, browser captures by source/capture, and actions by run/ordinal.

## Source states

Use `complete`, `partial`, `unavailable`, `stale`, `excluded` and `unsupported`. A checkpoint is complete only when every enabled, required provider succeeded within policy. Disabled or explicitly excluded providers do not count as failures. Resource-level errors remain visible.

If fresh browser data is unavailable, a checkpoint may explicitly reference retained last-known browser state with its original capture timestamp and `stale` status. Do not relabel it as newly captured. Compare sequence only within a source epoch; reject delayed events from superseded connections.

## Atomic persistence

1. Collect provider results outside a write transaction under fixed deadlines.
2. Validate, normalize and compute a content hash from meaningful resource state, not timestamps.
3. Insert checkpoint, source statuses and resources in one transaction.
4. Commit before publishing success. If unchanged, update separate observation freshness without rewriting immutable history; “Save now” may create an explicit checkpoint.
5. Perform retention as a separate bounded transaction after success.

Browser chunks are temporary staging, never recovery checkpoints. Persist the fully validated browser capture and its ingestion ID in one transaction before acknowledging; duplicate ingestion IDs return the prior result. The next periodic or debounced capture combines fresh browser state and desktop providers.

## Recovery protection

At startup, in one transaction, identify the previous session's latest useful checkpoint, create a pending recovery candidate and add a candidate pin before new captures can run. Prefer complete checkpoints with supported resources; if only partial history exists, offer it with warnings. A verified all-empty capture remains valid history but is not automatically preferred over useful prior work.

Multiple unresolved candidates can exist across repeated restarts. Retention never deletes any referenced pending candidate or user-pinned checkpoint. Dismissing or successfully resolving a candidate releases only that candidate's pin. A failed, cancelled or uncertain restoration leaves protection in place. Starting a restore also pins its checkpoint until its journal is resolved.

## Retention and migration

Apply age and count limits only to eligible unpinned automatic checkpoints. Retain manual checkpoints until explicit deletion or a separately visible manual-retention policy. Enforce the storage budget without silently deleting pins; surface storage pressure when policy cannot fit. Bound staging and logs separately.

Migrations are numbered, transactional where SQLite permits, and tested against prior versions. Create a verified backup before destructive migration. An older agent encountering a newer schema must refuse writes with a useful error. Never silently create an empty replacement database after corruption; preserve evidence, disable writes and offer explicit backup recovery.
